- [rust] Rust middleware that may or may not consume a request body must carry both outcomes in one enum built before any use; moving the body in one if-branch then using it later trips E0382 conditional-move errors. <!--id:1-->
- [workflow] Plan registries are one committed SQLite file (plans.db) per repo; never generate markdown or YAML plan artifacts. Read state with plans_show; write with plans tools only. <!--id:2-->
- [mind-plans] Never `git checkout <ref> -- plans.db` to "sync" the file: the working-tree copy holds uncommitted mind-tool writes and checkout overwrites them with no recovery path. Stage plans.db before any merge/checkout step that could touch it. <!--id:3-->
- [workflow] Reviews default to one quick inline pass over the diff; never spawn reviewer subagents for review gates unless the user explicitly asks for deep review. <!--id:4-->
- [merger] The mind CLI flocks plans.lock itself, so calling mind inside a merger flock self-deadlocks. Run mind update/export outside the flock (each call is atomic via mind's own lock) and keep git steps under the flock. <!--id:5-->

- [mind-registry] Never wrap `mind` CLI calls in a `flock` on plans.lock — every mind invocation takes that lock itself (open_registry → prepare → lock_registry), so the wrapper deadlocks it. Wrap only the git steps; mind self-serializes registry access. <!--id:8-->

- [workflow] Running `devctl test` (cargo/sccache) inside a `flock -c` can wedge the lock permanently: the sccache daemon inherits the flock'd fd and keeps the lock alive after the flock command exits, blocking all mind CLI/MCP calls. - [workflow] Daemons spawned inside a `flock -c` block (e.g. sccache during devctl test) inherit the lock fd and hold it forever, wedging every later mind command. Kill the idle daemon to release the lock, then rerun the bookkeeping. <!--id:18-->
- [testing] Never run persistence/integration tests with bare `cargo test` in this repo — DATABASE_URL points at the dev database, test rows persist there, and leftover rows produce phantom duplicate-key and money-sum failures. devctl test is the only suite path; it builds a fresh throwaway DB per run. <!--id:19-->
- [workflow] In devctl-style multi-instance setups, `app fresh-start` can reset the SHARED infra stack (dropping every instance database), while `app start` provisions only the named instance. Read the lifecycle command's blast radius before running it against a worktree. <!--id:20-->
- [devctl] In a devctl worktree, always pass `-i <instance>` to devctl subcommands. Bare `devctl migrate run` silently targets the shared erp_dev database. `devctl -i <name> app start` bootstraps a fresh tree: creates the instance DB, migrates, then builds (sqlx macros need the live schema). <!--id:21-->
- [git] Verify `git stash push` actually created an entry before `git stash pop` — a no-op push (nothing to save) makes pop apply the oldest foreign stash onto your branch. In shared checkouts, prefer `git stash push -m <label>` plus `git stash pop stash@{0}` by reference. <!--id:22-->
